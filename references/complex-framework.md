# 复杂框架图规范

用于表达多模块方法、模型架构、分层系统以及带共享组件和反馈机制的整体框架。沿用主 skill 的 SVG、自包含、配色和导出要求；本文件只补充复杂结构的设计与检查方法。

整体布局同时遵循 [规整版式与视觉设计](paper-layout.md)：优先以同高分栏、对齐分行或主区加辅助带构成紧凑的矩形图版，再按各分区的阅读任务安排内容；仅在需要解释内部机制时展开相应关系。

## 先建立结构，再选择视觉形式

从源材料建立两个互补视图：

- **模块层级**：系统包含哪些子系统，每个子系统拥有哪些内部模块；共享资源放在哪个层级。归属关系用分组表示，不能随意替换成箭头。
- **关系图**：节点之间传递什么，谁调用谁，哪些关系是并行、条件分支或反馈，哪些关系只在训练或推理阶段存在。

为模块和边赋予稳定 ID。节点至少记录 `id / 名称 / 类型 / 所属容器 / 输入输出 / 是否核心机制`；边至少记录 `id / 源端口 / 目标端口 / 关系类型 / 传递对象或条件 / 所属阶段`。简单部分可以合并描述，不必为绘图建立庞大数据库。

图中的关系必须能回溯到源材料。不要根据“框架图常见结构”擅自添加编码器、记忆、反馈、损失函数或验证模块。用户请求假想示例时，可自拟这些组成，但须明确它们只是示例设定。

## 根据结构选布局

| 结构特征 | 可用布局 | 优先解决的问题 |
| --- | --- | --- |
| 多输入、并行编码、融合 | 输入分列或分泳道，在融合处汇合 | 并行分支保持独立，不画成串行链 |
| 层级系统、嵌套模块 | 外层子系统分区，内层按局部网格组织 | 模块归属、共享边界和端口清楚 |
| 共享模型、记忆或数据源 | 主处理区旁设置共享区 | 区分读取与更新，避免重复绘制成多个实例 |
| 训练与推理 | 上下或左右分面板，共用模块做明确标识 | 区分参数更新、训练专用边和推理数据流 |
| 核心算法细节较多 | 总体框架 + 核心模块放大面板 | 放大图与原模块一一对应，不暗示新增阶段 |
| 交互系统和闭环 | 主路径集中，反馈沿外围通道返回 | 反馈目标精确，长边不穿过核心内容 |

可以组合布局，但先确定一个主阅读方向。同一排主容器默认顶底对齐，列宽可随内容复杂度变化；核心机制获得更多宽度或内部面积，简单输入输出使用紧凑窄栏。保持科学关系准确，通过内部重排和宽度分配实现外层整齐。

## 分配层级与空间

先在绘图说明中确定外层分区的具体比例，再确定各分区内部的行列、模块尺寸和连接通道。例如记录“输入区 / 核心区 / 外部系统 = 2:5:2”，还须写明该比例针对扣除外边距和通道后的可用宽度。

容器的内容区必须扣除：边框视觉范围、内边距、标题带、内部行列间隔，以及专用线缆通道。内部模块不能借用标题带或挤占连接通道。

跨边界连线如果需要经过标题带，预留明确的入口走廊，把标题文字的实际包围盒作为避让障碍。分区标题和边标签都要参加压线检查；只检查节点内部文字会漏掉这些冲突。边标签也须避开外层容器边框，不能仅因它位于两个节点之间就判定有足够留白。

复杂布局按以下顺序推进：

1. 确定矩形图版骨架和公共对齐线，布置子系统容器与辅助区，预留跨区域连接和回路空间。
2. 在各容器内放节点占位，定位融合、分叉和共享资源的接口。
3. 路由主连接，再路由依赖、读写和反馈；此时检查是否必须调整分区。
4. 渲染线框草稿，检查外轮廓、对齐、空白分布，再沿主路径、各并行分支和反馈路径检查可追踪性。版式松散时先重排，不直接进入图标精修。
5. 空间和关系稳定后，添加内部机制、精简标签和图标，再做视觉精修。

当最小字号或必要间距无法满足时，依次考虑重新分组、改变长宽比、精简重复标注、将核心细节放到第二面板。仅增大 viewBox 再缩回同一物理宽度不能解决可读性问题。不能以删除必要关系或把标签缩成小字解决拥挤。

层级只保留表达归属所需的深度。一般先尝试“系统分区 → 功能模块 → 内部符号”，更深的细节可使用放大面板；这不是禁止更深层级的硬限制。

## 用内部图形表达机制

框架图的细节来自方法，而不是更多装饰：

- 特征或表示可用向量条、矩阵、特征图堆叠，形状和数量应避免暗示未经证实的维度。
- 多候选过程可展示少量代表项及明确的省略符；不要把示意项数当成真实采样数。
- 融合、选择、聚合和比较使用不同的节点或短标签；汇线本身不能替代运算含义。
- 模型、工具、缓存和持久存储需要可辨识的视觉形式。图标能明确表达实体时复用图标，否则用简单矢量结构配关键标签。
- 同一个共享组件默认绘制一次。确需在不同面板重复出现时，用一致 ID、名称或共享标记说明其身份；外观相同不等于参数共享。
- 放大面板标记其对应模块；引出线采用与实际数据流不同的无箭头线型，并在需要时解释。

保留准确的短符号、模块名称和必要条件。图注承担完整解释，图内避免把每个模块的定义写成段落。主标题、分区标题、内部标签应有明确层级，但不要重复同一句信息。

## 区分关系并保持连贯

先定义边的视觉语法，在整图中一致使用。可按具体方法选择以下约定，已有论文约定优先：

| 关系 | 可用表示 | 注意事项 |
| --- | --- | --- |
| 主要数据流 | 实线 + 箭头 | 箭头指向消费数据的端口 |
| 控制、约束或条件依赖 | 虚线 + 箭头 | 不与“可选模块边框”混为一种含义 |
| 状态更新或反馈 | 独立走廊 + 箭头 + 必要短标签 | 线型可与数据流相同，但返回对象必须明确 |
| 组成 / 归属 | 容器或区域包含 | 不用箭头制造执行先后关系 |
| 参数共享 / 局部放大对应 | 无箭头连接或一致标记 | 与实际调用和数据传输区别开 |

只为实际存在的关系定义线型。两类以上不易自明的编码需要紧凑图例；颜色可辅助区分，但不能独自承担全部语义。

### 端口与跨区域路由

- 连接精确绑定到模块的命名端口，例如 `planner.output`、`memory.read`、`memory.write`。布局变化后重新计算端口坐标。
- 连接内部模块时，让线到达内部模块端口，不能只停在外层框上。若外层框本身代表黑盒接口，则明确显示该接口；线穿越外框时不需要在边界添加虚假箭头。
- 汇聚到同一运算的分支使用独立输入端口，或在显式融合节点汇合；不同数据流不能为了减少线条无条件合并。
- 共享总线只在语义允许时使用，并标明分支和连接点。交叉处无连接点不代表读者必然能辨认，优先用通道和节点排序减少交叉。
- 长回路沿框架外围或分区间的紧凑通道走线，通道计入矩形图版范围。为边上的条件和数据标签分配占位框，不能把它们临时塞进转角；也不能为绕行而任意拉开整图。
- 同一组并行线保持足够间隔，给每个箭头留出完整长度。需要不同方向的读写时使用明确的独立箭头或带标签端口，避免含义不清的双箭头。
- 调整节点次序或端口位置后，检查整条路径和它经过的所有容器，不能只检查起止点。

布局算法可辅助分层、排序和避让，使用环境已有工具即可；最终仍须校正标签、图标、端口和外层容器。不能把算法输出当作已通过视觉检查的成图。

## SVG 组织与绘制顺序

将模块树映射为语义分组，内部节点用父容器的局部坐标定位；将边的源目标与路径参数分开保存，避免直接在 SVG 中反复补绝对坐标。先统一坐标系，再做跨容器连接和边界测量。

检查实际 SVG 的父子分组与模块树一致，确保在编辑器中能够整体选择和移动子系统。单独的 `data-parent` 注释不能替代真正的 `<g>` 嵌套。跨子系统连线可以保存在独立图层；子系统移动后，通过生成脚本重新计算端口与连线，不能声称普通 SVG 本身具有自动吸附布线能力。

建议按背景分区、连接线、节点主体、文字图标及必要标注组织绘制顺序。嵌套容器可能遮住先绘制的边，需根据边所在层级安排图层；不能用大面积背景覆盖来隐藏错误路由。节点主体、标签及图标仍要保持可编辑分组，图层顺序不应破坏模块身份。

优先复用布局参数和内部 SVG 图元。若同一图标多次使用，每个实例的内部定义仍须具有唯一 ID；跨面板也不能重复定义相同 ID。

## 复杂框架专项检查

除主 skill 的通用检查之外，逐项核对：

1. **结构忠实**：模块树与源材料一致；分区不暗示不存在的归属；核心机制没有被通用图标遮蔽。
2. **关系完整**：沿关系表逐边对应 SVG。并行不变串行，融合操作清楚，反馈回到正确节点，训练专用边不进入推理路径。
3. **跨边界连续**：每条跨容器线可从源端口追到目标端口，没有被背景、标题带或内部节点遮断。
4. **共享对象明确**：读写方向和共享实例可辨认；放大面板和重复示意不会被误读为新模块。
5. **空间有效**：逐层检查子元素位于父容器的内容区；节点不占标题带，长边和边标签不穿过无关图元。
6. **视觉编码一致**：同类模块、线型、颜色、图标和面板标记一致；灰度下仍能区分关键关系。
7. **整体可读**：在最终论文尺寸下能辨认各分区和关键路径，在放大视图下能读懂内部细节；不是只有放大到屏幕全宽才可阅读。
8. **版式规整**：主要分区组成紧凑矩形图版，公共边线与标题基线一致，辅助区有序，没有无用途的大块空白。依照 [版式验收](paper-layout.md#版式验收) 检查，不能用路径无碰撞代替。

静态 SVG 检查器不验证模块归属、拓扑等价或路径避障。这些项目需要关系表核对、几何测量和实际渲染检查，不能因为检查器退出码为 0 就勾选通过。

对使用直角折线的框架，可从独立关系记录中检查：预期边与实际 SVG 路径一一对应、起止点匹配端口、每段避开无关节点内部、不同边不存在非预期交叉或共线覆盖，再用渲染测量检查全部文字与线段的间距。报告应明确是否计入描边、marker 和内部路径；中心线检查不能证明所有视觉边界无碰撞。

内部机制的图形同样参加内边距检查。特意通向边界端口的路径应明确标记并单独验证连接，不能把它当成内容越界，也不能将所有内部路径都豁免检查。

## 实绘验证用例

以下用例验证特定系统框架。对有限版面内的密集关系与局部细节，按 [高密度复杂图版设计](dense-mechanisms.md) 选择与当前任务相符的用例；已有测试通过不代表其他关系形态或内容领域均已验证。

检验复杂框架能力时，可用一个明确标记为假想的用例：双输入 → 并行处理 → 融合 / 规划 → 执行 → 外部环境 → 检查，并包含共享状态的读取更新及失败反馈。提前列出所有连接；要求展示子系统边界和至少一个模块内部机制。

该用例检查分支、归属、共享关系与布线能力，不是要求所有论文图都具有这些模块。记录实际渲染中发现的问题；没有执行该用例时，不宣称复杂框架已通过实绘验证。
